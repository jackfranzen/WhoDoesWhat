# WhoDoesWhat — implementation reference

Detailed implementation notes for contributors. For the user-facing overview, see [README.md](README.md); for the message-by-message network reference, see [SYNCING.md](SYNCING.md); coding agents should start with [AGENTS.md](AGENTS.md).

This document records current design intent and historical client observations. It is not an API contract, and some client-specific notes can become stale as Anniversary builds change. Verify uncertain behavior against the current code and client.

Large WoW addon (TBC 2.5.5 Anniversary) for managing raid assignments, roles, and buffs.

## Tech Stack
**In use:** Lua 5.1 (WoW Classic API) · AceGUI-3.0 + custom `CreateFrame` chrome (WdwFrame.lua) + modern Menu API (right-click) · AceAddon/AceConsole/AceDB-3.0 · LibClassicInspector (+LibDetours) for talent sync — caches in-range/peer talents, we consume `TALENTS_READY`; can't fetch, so out-of-range non-users stay unknown · AceComm-3.0 + LibSerialize + LibDeflate (copied from the user's WeakAuras) for the assignment sync layer (Sync.lua) · LibCustomGlow-1.0 (copied from NovaConsumesHelper) for the buffing bar's per-button glow.

## Coding Guidelines
* **Never edit `Libs/`** — treat all bundled libs as read-only; customize via overlays/wrappers/subclassing, never patch.
* **Logging:** verbose dev logs via `WhoDoesWhat:Print(...)`.
* **Class/spec metadata:** always from `WhoDoesWhat.Classes` (Data.lua).

## Features
* **Role & buff data (Data.lua):** all TBC classes/specs (icons, colors), collapsed categories, per-role default paladin buff priorities and default bans (backfilled to a full 6-buff order plus an `allowedCount` divider), custom roles. DB stores only deviations; `GetEffectiveBuffSetup` feeds the editor and `GetEffectiveBuffOrder` returns only the allowed prefix for assignment math. `PaladinBuffs`/`CCSpells`/`WarlockCurses` use TBC max-rank spellIds with Classic Era overrides in `ClientFeatures.lua`; Classic also adds Curse of Shadow. Wrong ids surface as "?" (CC icons via `GetSpellIcon`). `RaidTargetMarkers` skull-first; chat tokens = lowercased marker names.
* **Hunter pets (`hunter_pets` pseudo-role):** NOT assignable or customizable — removed from the Hunter role/category lists (no Set Role menu, Members page dropdown, or Role Preferences page offers it; a one-off Core.lua migration clears old assignments + its customization). Registered by hand in `RolesAndCategories` (like Non-raider) so stale synced assignments still resolve. Instead every hunter automatically contributes one virtual pet (`GetPetMembers` in Assignments.lua, exported on `Assign`): `"<Hunter>'s Pet"` entries (apostrophe can't collide with character names; `owner`+`isPet` fields) that live only in the paladin-buff math — demand votes + own `ComputeBuffGrid` rows wanting `HunterPetBuffOrder = {might, kings, light}` from Data.lua (deliberately NOT backfilled, so a fully covered pet shows an empty cell). Non-raider hunters contribute no pet. In the buff grid the pets form their own section immediately after Warriors; they retain Hunter metadata/colors and use the pet role icon. Hunter pets ride the **Warrior blessing group** — a Greater Blessing on a Warrior reaches them (PallyPower files pets under Warrior for this reason). The shared plan matches each pet's wants across the **full** paladin pool like any other row, with a `PET_GREATER_BONUS` (200 — above any talent gap, far below one position step) for pairing a pet with the paladin whose Warrior Greater IS that blessing; cells that don't match the Warrior Greater become individual **Normal** blessings. So a shared Greater wins ties but never costs the pet a higher-priority blessing (a Kings-talented paladin holding the Warrior Might Greater gives the pet Kings while someone else covers Might). `PallyPowerBridge` and `GetPaladinBuffJobs` consume that same plan and Warrior Greater decision; unresolved real pet names and fake hunters' pets cannot become castable individual targets.
* **Buff tracking (BuffTracking.lua):** live scan of which paladin blessings and configured status auras are active on each group member **and hunter pet**, matched by localized aura name (rank-proof, Greater or Normal). Modern `C_UnitAuras.GetBuffDataByIndex` (indexed `UnitBuff` fallback), per-unit on `UNIT_AURA` + a 3s full-group backstop poll. In Classic the aura LIST is available at any range for group members; the last observed expiration is retained when duration goes stale out of range. Dead is a directly-scanned status, not an aura. Pets are keyed `"<Owner>'s Pet"` to match the plan. API: `WhoDoesWhat:HasBuff(name,key)` → true/false/nil, `GetActiveBuffs`, and `GetBuffTimeRemaining`. `RefreshBuffingGridView` is the shared repaint hook.
* **Paladin Buffing Bar (PaladinBuffingBarView.lua):** a movable, Nova-style **secure** bar — a clickable alternative to PallyPower that casts blessings directly (works with or without PallyPower installed). One button per CLASS the local paladin is assigned, from `GetPaladinBuffJobs` (on `Assign`), which collapses the active WDW/PallyPower plan into a class Greater + per-player Normal exceptions. PP source mode prefers a co-installed addon's live tables and falls back to WDW's observed wire mirror. **Left-click** casts the class Greater on a member (rotates through all resolvable members for range robustness); **right-click** cycles every assigned member's planned Lesser Blessing, including recipients of the class Greater, ordered missing first and then by shortest remaining duration. Secure `Execute`/`WrapScript` rotation (PallyPower's proven pattern, snippet branches on `button`) is baked out of combat and rebaked on `PLAYER_REGEN_ENABLED`; cast targets are unit tokens (`[@raid5]`/`[@raid5pet]`). Existing class buttons still repaint their effective job, `buffed/total` count, range state, and glow in combat; protected spell/target attributes and any added/removed class-button layout wait for `PLAYER_REGEN_ENABLED`. **Hunter pets bucket under the Warrior button** — a Greater on a Warrior reaches hunter pets, so a pet whose want matches the class Greater is covered for free; right-click can still top the pet up with its planned Lesser (real pet unit via `GetPetUnitInfo`). A pets-only bucket shows the pet icon, while a mixed one shows the class icon + a small pet badge. Per-button count comes from `HasBuff`, the icon greys when nothing's castable in range, and LibCustomGlow PixelGlow marks a reachable missing member. Alt-drag to move; growth is RIGHT/LEFT/CENTER, encoded as the saved anchor point (`GROW_POINTS` → `TOPLEFT`/`TOPRIGHT`/`TOP`) so a saved position is self-describing and a mode change re-derives it from the current rect — CENTER stores the midpoint via `GetCenter` and `ClampPosition` keeps both halves on screen. The title strip reads `Paladin Bar` at the left with a separate grey `WDW`/`PP` source token a point smaller at the right end, and the bar's minimum width respects both string widths so they can't collide. Its tooltip carries one grey line naming the source ("Buffing data is powered by …"), then double-lines for Alt-Drag / Shift-Left-Click (Buffing Grid) / Shift-Right-Click (`OpenAddonSettingsView("Paladin Bar")`). **Status Bars** moved to the same pair (`StatusBarsClick` now gates on shift for both buttons instead of bare right-click), so the PallyPower row's plain-left-click Differences shortcut had to start ignoring shift-clicks. Local `settings.buffingBar*`: master toggle + a Developer "preview as any real/fake paladin" dropdown; fake-raid pets show grouped but aren't castable (no real unit).
  In PP source mode a grayscale Engineering-icon button stays at the far right, keeps the `PP Buffs` bar at button height even when PP assigns nothing, counts active real-raider classes with no PallyPower class blessing assigned to that paladin, and opens PallyPower's Blessings window when the addon is installed. Pets, fake raiders, and Non-raiders do not contribute. The bar always reserves at least three horizontal button slots.
  **Self-buff buttons** — "Paladin Aura Helper" / "Righteous Fury Reminder" (`settings.buffingBarAuraButton` / `buffingBarRighteousFury`, both default on, Settings > Paladin Bar, rows 2 and 3) lead the row at the left, split from the class buttons by a 1px divider in a 9px gap; the divider only draws when a class row follows it, and both buttons act on the LOCAL player (test mode renders them for layout preview only). Both gate on a RESOLVED paladin, which is the whole class check — outside test mode `ResolveBarPaladin` only names one when the local player is a paladin, inside it only when one is picked — so test mode with an empty paladin dropdown falls through to the bar's "No Paladin selected for testing." hint instead of offering buttons for nobody. Neither shows a coverage count — the slot under the button stays empty except for a countdown. **Aura swapper:** `WhoDoesWhat.PaladinAuras` (Data.lua) lists the client's auras by BASE-rank spellId — Devotion, Retribution, Concentration, the three resistances, Sanctity, plus Crusader Aura on TBC — with names/icons resolved off the id at load and nameless entries dropped. The bar filters to what's in the spellbook via `GetSpellInfo(name)` (which nils for unknown spells, so the talent auras and level-62 Crusader fall out on their own). Hovering opens a picker of every castable aura, left-click casts the one being offered; the swapper carries **no tooltip of its own** — the picker replaces it. The picker (`CreateAuraMenu`/`ConfigureAuraMenu`) is a protected panel built like the class buttons' player menus — shown from the swapper's `_onenter` snippet with `RegisterAutoHide`, so it closes on mouse-out — carrying the player menus' own header strip verbatim (same `PLAYER_HEADER_H` geometry, colours and blue two-line click hint) and floored at `PLAYER_MENU_W` so that hint has the room it has over there, with the icons laid out below in captioned rows: "Auras" first, then "Resistances" off the `resist` flag in `PaladinAuras`. Each icon shows the CLIENT's own spell tooltip on hover — `SetSpellByID`, falling back to a `spell:` hyperlink on builds without it — off the rank the paladin actually knows (`select(7, GetSpellInfo(name))`, which resolves the highest rank for a rank-less name; the base-rank id covers test mode), plus a green "Running." line. Each icon is a `SecureHandlerClickTemplate` button carrying its own `astep`/`auraMacro`, and its snippet writes both onto the swapper through a frame ref, so picking an aura keeps working in combat; the layout and that baking are combat-locked like every other secure write on the bar. `WirePlayerMenus` is now `WirePopoutMenus` and hands the `otherMenus` close-list to the self-buff buttons as well as the class buttons — the swapper contributes its picker and closes the player menus, Righteous Fury owns no popout and only does the closing (`CLOSE_MENUS_SNIPPET`) — so sliding along the row swaps popouts instantly instead of waiting out the previous one's 0.25s auto-hide. Both self-buff buttons now take `SecureHandlerEnterLeaveTemplate`, so their tooltip/`OnLeave` scripts are **hooked, not set**, or the template's secure dispatch would be thrown away. The pick is persisted to `settings.buffingBarAura` from the option's own `PostClick`, and `UpdateAuraMenu` paints a gold border on the offered aura and full colour on the one actually running; with nothing saved the selection adopts whatever aura is already running, so a first login doesn't open on a false alarm. The icon greys with a red PixelGlow whenever the offered aura isn't the one running. **Righteous Fury:** appears only while the resolved paladin holds a tank role (`IsMarkedTank`, which is where prot talents reach this via role auto-detection); one fixed self-cast, so its secure attributes are set once at creation. Red glow + grey icon when it's down, yellow glow with an `m:ss` countdown in its last ten minutes, nothing for the rest of its half hour. Both repaint from the bar's existing 0.5s tick plus a `UNIT_AURA`-on-`player` shortcut (which updates only these two buttons rather than running the whole repaint), so a cast lands immediately; `SetButtonGlow` now tracks the glow COLOUR so the red↔yellow switch restarts the animation. **Every tooltip the bar owns** — the two self-buff buttons and the title strip — opens where the class buttons' player menus do, so none of them lands on top of the bar: `PositionPlayerMenu`'s direction rule is factored out as `PopoutDirection(frame, needed)` and all callers use it, anchoring `TOPLEFT→BOTTOMLEFT` (down) or `BOTTOMLEFT→TOPLEFT` (up) off the `buffingMenuGrow` setting with the same flip when that side is cramped. Because GameTooltip only knows its height once populated, `ShowBarTooltip` owns it with `ANCHOR_NONE`, calls the frame's own `FillTooltip`, shows, then re-anchors; an optional `frame.tooltipAnchor` hangs it off something else, which is how the title strip anchors to the whole bar rather than to the strip (anchoring to the strip would put it over the button row). `RefreshBarTooltip` re-runs that whole build from every repaint path — guarded on `GameTooltip:GetOwner()` still being that frame — so a rotated aura, a landed cast and a ticking countdown all update under the cursor.
* **Talent sync (TalentScanning.lua):** `TALENTS_READY` → `AutoAssignDetectedRole`: fill empty, follow respec, never fight manual override on unchanged spec (compare `db.profile.talentSpecs`). A client's FIRST detection (`talentSpecs` nil) never overrides an existing assignment — it may be manual or synced from a client that could inspect in range; without this, two clients with different caches tug a player between roles. **Single-writer Blizzard flags:** the Blizzard role flag (`UnitSetRole`) has no range check AND every write fires `GROUP_ROSTER_UPDATE` on every client — which drives each client's reconcile sweep. Two clients with differently-stale boards therefore ping-pong one player's flag forever at the sweep interval, re-announcing "X is now Damage Dealer" on each bounce. Two defences, both required:
  * **Election** (`BlizzardRoleWriter` in Core.lua, behind `CanSetOthersBlizzardRole`) names ONE writer for OTHER members' flags. The LEADER wins whenever `Sync:RunsCompatibleProtocol(leader)` — the PROTOCOL match matters, not mere presence: senders are recorded as peers *before* the protocol check, so an out-of-date leader reads as "runs the addon" while ignoring every board we send, and electing them means their stale board stomps everyone forever. Without such a leader, the alphabetically first permitted member on our protocol is elected — name order is identical on every client, so everyone picks the same writer with no negotiation round-trip, which is what keeps ten assistants from writing at once. nil (nobody eligible) means nobody writes, which beats everybody writing.
  * **Settle delay** (`SETTLE_SECONDS`/`pendingSettle` in UnitMenuExtensions.lua) fixes the flicker the latch can't see, because it isn't a loop — it's one stomp and one correction. Every client writes its OWN flag the instant the user picks a role, but the board justifying it rides the 2s sync poll (`POLL_INTERVAL`), while the flag write fires `GROUP_ROSTER_UPDATE` and wakes everyone's 1s roster sweep (`TalentScanning.lua`). For ~1s every other client can see the flag change but not the board change, and "corrects" from stale evidence; the board then lands and the flag flips back. So a **sweep** (`ReconcileBlizzardRoles`, which passes `deferrable`) that finds the flag on a DIFFERENT REAL role records it, writes nothing, and re-checks after 5s via a self-arming timer — if the board catches up the disagreement evaporates at zero writes. `NONE` is never deferred (kick/reinvite, nothing in flight). Explicit user actions never wait. Paired with `Sync:PushSoon()` (0.25s debounce, called from `SetAssignedRole` **before** the flag write), which removes the race at the source rather than mitigating it. Considered and rejected: parsing `ROLE_CHANGED_INFORM(_WITH_SOURCE)` off `CHAT_MSG_SYSTEM` — unverified on 2.5.x, and it reports who set the flag rather than what the board says, which is the thing that was stale.
  * **Write latch** (`lastWritten` in UnitMenuExtensions.lua) breaks the loop the election can't: your OWN flag is always yours, so the player themselves is always a potential second writer. Keyed by ROLE ID, so it self-invalidates when our board's opinion changes — no hunting write sites. If we already wrote this role id and the flag now reads a *different real* role, we stand down (logged under `logRolePromotion`) instead of re-asserting. A flag reading `NONE` is not contested (that's the kick/reinvite reset the roster sweep repairs), so it still re-applies freely. Both sides stand down after one exchange and the flag settles on whoever wrote last; the underlying board disagreement is a version problem to fix at the source.
  * `ReconcileBlizzardRoles` remains the sole other-member flag write path (own edits, `Sync.ApplyState`/`ROLE`, roster sweep, `PLAYER_REGEN_ENABLED`); `AutoAssignDetectedRole` no longer gates on authority — `ApplyBlizzardRole` decides internally whether to write, queue an issue, or do nothing. `UnitSetRole` everywhere only fires when the flag actually differs (re-setting an identical flag re-announces to the group and fights other role addons). Quiet (no announce). **Combat:** patch 2.5.6 protects `UnitSetRole` and `RaidFrame:Show` from addon execution, so role writes and the tank promote window are deferred until `PLAYER_REGEN_ENABLED`. The **main-tank demotion is deferred too, by choice rather than protection** — `ClearPartyAssignment` is callable mid-fight, but re-promoting isn't (`SetPartyAssignment` is protected: Raid tab → right-click → menu, during the pull). A fight that swaps someone tank→dps→tank would charge the leader that every time, so the mark is held for the duration and the same `PLAYER_REGEN_ENABLED` reconcile demotes afterward if they're still off a tank role. **The demotion half is independent of the flag half:** it runs for ANY role including `nil`, because "role cleared" and "role has no `wowRole`" both mean not-a-tank. `ReconcileBlizzardRoles` therefore no longer filters its loop to members with a resolvable `wowRole` (that filter was what left a main tank marked forever after a clear or a switch to a wowRole-less custom role), `SetAssignedRole` calls `SyncBlizzardRoleState(name, nil, unit)` on the clear branch, and a contested flag stands down without skipping the demotion. Marking a main tank **Non-raider** (`wowRole=false`) now demotes them too. Undetectable roles (warlock_firetank, druid_dreamstate, feral tank, customs) untouched. **Master opt-out:** `settings.manageBlizzardRoles` (Settings > General, `WhoDoesWhat:ManagesBlizzardRoles()`) gates `ApplyBlizzardRole`, `ReconcileBlizzardRoles` and `StartPromoteWatch` — WDW's own board is unaffected, only Blizzard's group state is left alone. Local and deliberately unsynced: it's a per-client escape hatch for a raid where flags are being fought over, and one raider opting out must not opt everyone out. Re-enabling runs a reconcile immediately rather than waiting for the next event. Flags: `LOG_TALENTS`/`LOG_TALENT_COMMS`.
* **Paladin buff-talent scan:** per-paladin ranks — Improved Might (0-5), Improved Wisdom (0-2), Kings (0-1), Sanctuary (0-1); Kings/Sanctuary are talent-GRANTED (untalented can't cast). Stored in `db.profile.paladinBuffTalents` (nil = unscanned, ≠ rank 0). Ranks read from the client's **native `GetTalentInfo`** matched by hard-coded `(tab, tier, column)` — NOT the library's positional cache, whose index order is shuffled on the Anniversary client (LibClassicInspector assumes native order == its static table; it isn't, so its ranks land under the wrong talent). Only reads on a fresh inspect (`isInspect`) or the local player — a cache replay/broadcast has no live native data, so it's skipped rather than zeroed. `active` spec only (via `GetActiveTalentGroup(isInspect)`), which is what they can cast now. Versioned wipe: `buffTalentScanVersion`.
* **Kick/reinvite catch:** `TALENTS_READY` fires only on data arrival, so rejoiners sit stale; debounced `GROUP_ROSTER_UPDATE` sweep replays from cache (cache-time gated) + `ReconcileBlizzardRoles` re-applies drifted role flags (leader-only for others; see the single-writer note above).
* **Local-player self-scan:** the library never fires `TALENTS_READY` for the player, so a `selfSync` frame replays the pipeline for our own GUID on `PLAYER_ENTERING_WORLD` / `CHARACTER_POINTS_CHANGED` / `PLAYER_TALENT_UPDATE` / `ACTIVE_TALENT_GROUP_CHANGED` (dual-spec swap changes castable blessings). Last two `pcall`-guarded (not on every build).
* **Assignment model (Assignments.lua):** on `WhoDoesWhat.Assign`. Section defs are MODEL-ONLY vocabulary (key/title/store/noun/whisperLead/spells/targetPlayer/autoRows/multiMarker/GetWarning — view-only flags were removed when the sections were hard-coded into Views/Sections/), `SectionByKey`, `GetEligibleMembers` (Developer Mode lifts filter) / `MembersOfClass` (strict), marker/spell/target text (`{skull}` tokens vs words), whisper collectors (named per section: `CollectTankWhispers` etc., generic ones kept for future sections) + `MassWhisper` (0.25s stagger vs throttle), `ComputeBuffGrid`/`ComputePaladinBuffSummary`/`CompileBuffRules` (derived paladin coverage + custom rules — see below), `AutoAssignWarlockCurses`/`ClearTankAssignments`/`ClearMisdirectAssignments` (exported for the views' header buttons), `PruneDepartedAssignments`, `SetAssignment` (exclusivity + pairWith + repaint; curses only now).
* **Main window (/wdw):** two scrollable columns. Both dimensions track the view mode in `ApplyViewMode`: full board = `FRAME_W` 892 wide; Paladin-only narrows to `NARROW_FRAME_W` 380, hides the permission strip so it can't collide with the buttons, drops the scrollbar (`scrollBarHideable` + reclaims its reserved width by anchoring the scroll to `-MARGIN`) and centers the lone box (`f.columns[COL_LEFT].x` offset). Height auto-fits the visible content each refresh (`f.scrollTop + content height`, clamped to `MIN_FRAME_H`..`MAX_FRAME_H` 130..550) so Paladin-only view is a short low-profile window and the full board grows until it scrolls. Boxes anchor-chained within their column (height change ripples only that column). Uneven: `LEFT_COLUMN_W` 330 (the compact Buffing Rules minimum for Paladin Buffs/Warlocks), right 500 (Tank + busy dynamic rows — CC/Misdirect + future custom sections). Section headers sit 5px below the box top with no separator before the first row; their titles use the normal UI font at +2 size, near-white, with a thin outline. Row dividers are replaced by touching, fully opaque alternating fills blended toward white. Paladin, Warlock, and Misdirect panels derive strong dark tints from the Paladin, Warlock, and Hunter colors in `Data.lua`; Tank and CC remain on the neutral section palette. Scroll child needs explicit `SetPoint`. `RefreshMainAssignmentsView()` repaints externally. * **Roster issues (ActionItems.lua):** the model behind the Members window's warning gutter, the toolbar count and the WDW Status row. **The merged row states the same fact three times over,** because the interesting part is where the three disagree. The **Group role** column writes Blizzard's flag directly via `UnitSetRole` (local `SetGroupRole`, gated on `UnitIsUnit(player)` or `CanSetOthersBlizzardRole`, and it clears the write latch so a later auto-write doesn't read the hand-picked flag as contested); the **WhoDoesWhat** column runs `SetAssignedRole`, which stores the spec and pushes the flag to match. Picking IS the fix, in whichever direction is right for that row. `SetGroupRole` is deliberately NOT gated on `ManagesBlizzardRoles()` — that switch stops WDW writing flags on its own initiative, and a person opening a dropdown IS the initiative. The WDW dropdown is the Members one, not the old Action Items one: it keeps the unit menu's full menu (class + custom roles, divider, **Non-raider**, and a passive disabled "None" while roleless). The **Talents** column is evidence, not a control: the role(s) the cached `LibClassicInspector` spread reads as, stated as icon + name exactly like the two columns beside it, with the raw per-tab spread one hover away (`GetTalentSnapshot`; a grey "not scanned" when nothing is cached — an unknown spread must not read as a player with no points) and a **Rescan** button pinned to the row's right edge. Feral druids get *two* roles (cat and bear share the tree, so the points genuinely can't tell them apart and one would be picking a side). Rescan runs `RescanPlayerTalents` — the single-player form of `RescanUtilityTalents`: replay the cache, then `DoInspect`. It is ungated by permissions, because an inspect writes nothing to anyone's board. While the request is outstanding the button reads **Queued** and is disabled; `rescanPending` maps player key → expiry, cleared by `OnTalentsReady` and expiring after `RESCAN_TIMEOUT` (10s) so an inspect that never answers — out of range, combat, logged out — doesn't leave a dead button for the rest of the raid. It is also disabled with no unit at all (a fake raider, or someone who has since left). **Disagreement is decided by plain majority, and the blame goes on the odd one out** (`RowDisagreements`, ActionItems.lua): a resto shaman the board and his talents both call Restoration, flagged `DAMAGER`, has *one* thing wrong with him, and naming all three would make the reader do the elimination the model already did. Each answer counts how many others it agrees with; anything below the best score, and in a disagreement, earns a sentence. When nothing scores an agreement — a two-way mismatch with no third answer, or a three-way split — there is no odd one out, so it emits ONE line naming the parties rather than accusing each in turn. Emitting one per accused answer was right while each lit its own gutter icon, but collapsed into a single tooltip it printed the same sentence forwards and backwards, and inflated the issue COUNT so that one wrong role read as two. Only answers we *have* take part: an uninspected player or an unset flag is unknown rather than wrong, and a warning on top of that would fire on most of the roster the moment a raid forms. Pairs that can't be compared sit out too — the group flag only names tank/healer/dps so it is compared at that coarseness, and `TalentsCanJudgeRole` excludes roles no spread can name (`warlock_firetank`, `druid_dreamstate`, custom roles), because blaming a Fire Tank warlock's TANK flag for his destro points is a warning no rescan could ever clear. The talent half exists at all because `AutoAssignDetectedRole` deliberately lets a *first* sighting lose to an existing assignment — a role picked before anyone could inspect them would otherwise sit on the board forever. **Collapsing three per-column warning icons into one gutter cost the at-a-glance read** — the icon's column used to name the guilty answer before you hovered — so the sentences now have to say it, which is why they are phrased as full clauses ("Group role (Damage) disagrees with …") rather than as labels. **There is deliberately no fix button** — neither per row nor a Fix All, and `GuessRoleId`/`PREFERRED_GUESS`/`suggestedId` went with them. Both applied a spec guessed from Blizzard's flag, which is the *least* trustworthy thing on the row: Blizzard drops every new raider on `DAMAGER`, and pending rows are most of the list, so "fix" mostly meant writing that guess onto the board in bulk. Talents are the real evidence, so the column offers them and you pick from the dropdown. **Permission and combat both simply disable the dropdown**, with the reason in its tooltip (`blockedReason`). The old window swapped an unwritable column for plain text on the grounds that permission is a standing fact while combat passes; the merged row disables in both cases instead, since a disabled dropdown already reads its value out, which is all a read-only column wanted to do — and one behaviour per row beats two. Rescan sits outside the whole scheme (looking at someone's talents needs no rights). The two gates differ by column: the WDW column takes `CanEditRoleOf`, the Group role column takes `CanEditGroupRoleOf(name, unit)`. That takes the resolved `raidN` token as a CONVENIENCE, not a requirement, falling back to the player key, since WoW accepts a group member name as a unit and `ApplyBlizzardRole` already relies on that (`unit or playerName`); requiring the token instead greyed the whole column and dropped the unit `SetAssignedRole` needs to push the flag. It returns `ok, reason`, and the reason is what the greyed dropdown tooltip shows, so rank and combat can be told apart on hover. **Manual and automatic flag writes are gated differently, and that split is the point.** A MANUAL write — a person picking a group role, or picking a WDW role and expecting the flag to follow — takes only `CanSetOthersBlizzardRoleManually()`, i.e. `PlayerCanSetGroupRoles` (the WoW rank the server itself demands: raid assist / party lead), plus own-row always. An AUTOMATIC write — talent detection settling a newcomer, the reconcile sweep pushing the whole roster — still takes the single-writer election `CanSetOthersBlizzardRole()`. `ApplyBlizzardRole(unit, playerName, role, manual)` carries the distinction, `SyncBlizzardRoleState` and `SetAssignedRole` thread it, and the four human-click call sites (unit menu ×2, Members dropdown ×2, PallyPower Diff, `RemoveRaidCustomRole`) pass `manual = true`. Manual writes also skip the `lastWritten` loop-breaker: standing down is for automatic re-assertion races, and a person re-picking a role someone else overrode is asserting on purpose. **Why the split:** the election returns the raid leader whenever the leader runs WhoDoesWhat, so gating manual picks on it left every assistant's dropdown dead in the normal case — and no tooltip could usefully explain that. There is no storm to prevent for a single deliberate click; the election exists to stop several clients writing the same flag on their own initiative. The rank check is not redundant with board permissions: those err **open** when the raid leader doesn't run WhoDoesWhat (`PermissionsOpenReason`), which is exactly when a rank-0 raider reads as fully permitted while the server refuses every `UnitSetRole` they make. `PlayerCanSetGroupRoles` is also a candidacy requirement in `BlizzardRoleWriter` — without it the election picked such a raider and produced a writer who wrote nothing. **Known regression from the merge:** finding three flagged rows in a forty-row bucketed list is worse than working down a three-row filtered window. The overview strip's issue count is the mitigation; sorting flagged rows to the top of each bucket was considered and skipped, since it would break the class-then-name grouping the page is scanned by.

Four modes — board entry / library custom role / built-in / create. The buff list is editable in all but **built-in**, whose order *is* the default: change one by overriding it for the raid (Custom Roles > Add (+), categories included) or by copying it into a custom role. A built-in role therefore has no Save button at all, no group-role dropdown, and no reorder arrows, with Create a Copy alone in the bottom-right corner. The arrows sit on each row's right edge so hiding them moves nothing; the group-role dropdown sits under the name field (label-less) and pushes the left-aligned buff heading and list down a row when shown, which is the whole difference between `FRAME_H` and `FRAME_H_CUSTOM`. A read-only role states its group role as an icon in front of its name ("[DPS] Fury") instead, so it needs no row. The `Never assigned` divider is grey, small, and hidden whenever the list can't be reordered. The status line above the buttons carries exactly one message — a warning that a board edit affects the whole raid — and is empty in every other mode. Order resolution is board override → custom role's own order → defaults. Taking anything off the board always confirms first, through `ConfirmRemoveRaidRole` (CustomRolesSection.lua), which both the row's `[x]` and the editor's Remove call so the two can't warn about different things. **Custom roles require name + class + group role**; the old "Assign role" opt-out checkbox is gone, so `wowRole` is always one of `dps`/`tank`/`healer`. `ValidateCustomRole` enforces this in Data.lua (not just the editor) and `CreateCustomRole`/`UpdateCustomRole` return nil/false with a printed reason when it fails. Reason: a role with no `wowRole` can't drive the group-role flag, and a main tank switched onto one couldn't be recognised as no-longer-a-tank, so the MAINTANK mark stuck. Legacy custom roles saved with `wowRole=false` are NOT migrated — they open showing DPS and are fixed by saving; the demotion pass below covers them meanwhile.
* **Unit menu (UnitMenuExtensions.lua):** `Menu.ModifyMenu` on self/player/target/party/raid. "Set Role" pop-out (persists, sets role flag, announces); tank-marker grid (multi-select; checking moves the marker onto that tank's row, unchecking clears just the marker — rows are roster-managed), CC target grid, misdirect pop-outs mapping onto stored rows (overwrite covering row or create; one sheep/mage, one tank/hunter). Below a divider: **Non-raider** (`non_raider`, Data.lua) — classless pseudo-role for anyone sitting out; its pseudo-class lives outside `Classes` so Role Preferences never lists it. Non-raiders drop out of buff demand votes, class-filtered rosters (buff/curse dropdowns + pools; `GetEligibleMembers` filters them on any class-filtered query), and the buff grid; marking someone Non-raider clears any paladin-buff rows (and override locks) they held.
* **Main-tank promote (RaidMenuExtensions.lua):** `SetPartyAssignment("MAINTANK",...)` is PROTECTED — can't promote (demote via `ClearPartyAssignment` works, auto for non-tanks). Instead, play the raid-warning sound and bounce an arrow at the player's row after the leader opens Blizzard's Raid tab; `GROUP_ROSTER_UPDATE` cleans up on success. **Multi-tank:** several tanks can be pending at once (`pendingPromotes` set + pooled per-name arrow/glow highlights). Pending entries clear when promoted, no longer tanks, or departed. The addon never calls `ToggleFriendsFrame`, `RaidFrame_LoadUI`, or `HideUIPanel`: current 2.5.6 builds can carry addon taint from an otherwise-allowed out-of-combat panel open into a later native in-combat `RaidFrame:Show`. A lightweight poll notices when the leader opens the Raid tab. Highlights stay parented to `UIParent` and only anchor visually to `RaidGroupButtonN`; reparenting addon frames into that protected hierarchy also risks taint. `StartPromoteWatch` is idempotent per player, and its klaxon is coalesced on a 1s window so a sweep turning up three tanks is one ping, not three overlapping raid warnings. Arrows are raised by **anyone who could actually promote** — `CanPromoteMainTank` (leader or assistant), *not* the flag-writer election: promoting is not a write we coordinate, it's a row we point at for a human to click, and gating it on the single writer meant exactly one person in the raid ever saw the prompt (and nobody at all when the leader doesn't run WDW). Entry points are edge-triggered — a direct tank-role set (`SyncBlizzardRoleState`) or the first-scan sweep in `OnTalentsReady` — so `SweepPromoteWatch` covers the transition neither catches: **our own rank changing**. A `rankWatcher` frame fires it on the false→true edge of `CanPromoteMainTank` only, since `GROUP_ROSTER_UPDATE` fires on every `UnitSetRole` anyone makes and the sweep walks the roster. Without it, an assistant promoted *after* the tanks were assigned had an empty `pendingPromotes` and saw nothing on opening the Raid tab, indefinitely — opening the tab only draws pending entries, it never discovers them.
* **Feral tank detection:** cat DPS and bear tank share the Feral Combat tree, so `SPEC_ROLES` can only guess `druid_feral_dps`. `OnTalentsReady` upgrades the guess to `druid_feral_tank` when the player already reads as a tank — holds the WDW feral-tank role, is flagged `TANK` (`UnitGroupRolesAssigned`), or is a promoted MAINTANK — so a bear that joined pre-flagged as tank isn't detected as DPS and doesn't get its TANK flag stomped.
* **Group messaging:** `WhoDoesWhat:SendGroupMessage(msg)` — RAID/PARTY/silent solo.
* **Editing permissions (Permissions.lua):** raid-only (party/solo always open); rule stands down wholesale (free-assign, gray note says why) in battlegrounds (`IsInInstance()=="pvp"`; sync uses INSTANCE_CHAT there) and when the current leader isn't known to run WDW (`LeaderRunsAddon` checks `syncPeers` — every comm sender Sync hears from, session-only, never wiped; leaderless moments err open; checked live so leadership changes take effect at once); the RAID LEADER picks who edits the board: `leader` / `assistant` (one named player) / `assists` (default — matches the old assist-gating) / `everyone`; leader always may. Setting lives in `db.profile.permissions {mode, assistant}`, rides the sync snapshot, resets to default on group leave. Enforcement is layered: `RequireEditPermission()` backstops every Set\* API (incl. `SetAssignedRole` for others; own role ALWAYS settable — `CanEditRoleOf`), `PruneDepartedAssignments` no-ops read-only, Sync gates broadcasts both ways. `PlayerCanEditAssignments(name)` ranks via `GetRaidRosterInfo`. UI: main view renders read-only without rights — dropdowns swap to plain-text lines (`row.roText`; class colors survive, unlike gray disabled dropdowns), \[+]/\[x]/clear-all/custom-editbox/mail (row + header) hidden, Auto greyed (not hidden) with a permission tooltip that survives the class-disable pass, warnings (except on unassigned rows — a to-do a viewer can't do) + demand + Grid/Info/Calc pop-outs stay, header buttons re-anchor right-aligned around hidden ones (`LayoutHeaderChain`, rightmost-first chains) and text buttons size to their labels; leader gets an "Editing:" picker dropdown top-left (level-2 assistant list via `UIDROPDOWNMENU_MENU_VALUE`), others a gray note naming the rule. Unit menu: pop-outs (tank/CC/MD) require permission, otherwise replaced by gray read-only summary lines of that player's assignments; own Set Role stays live. MembersView dropdowns permission-gated the same way.
* **Assignment sync (Sync.lua, AceAddon module "Sync"):** whole-board sync between WDW users in a group. Syncs roles (`assignments`), tank/CC/misdirect rows, non-paladin static rows (warlock curses), and the permission-gated raid-wide `PallyBuffSource`; **paladin buff rows deliberately excluded for now** — instead providers broadcast their own relevant utility ranks: paladin blessing talents, warlock Improved Healthstone, priest Improved Fortitude, and druid Improved Mark plus Improved Thorns/Brambles (read natively on the sender). A join/reload client's initial HELLO also carries only its three talent-tree totals, letting every WDW peer immediately run the existing class/tab role inference; LibClassicInspector remains the ongoing full-talent source. A fresh direct inspection of another roster member can additionally send a deduplicated `OBSERVE` with the target's three totals and exact relevant utility ranks; any raider may contribute this evidence, receivers validate it against their roster and infer the role themselves, and the leader relays accumulated non-WDW observations to later joiners. Conflict model: leave group → whole board wiped incl. permissions and PallyBuffSource (talent caches survive); join group → a compatible leader is the source of truth (joiner HELLOs, ordinary peers stay silent, leader whispers the full snapshot plus its current peer/version/utility-rank directory, applied unconditionally + popup if it overwrote a non-empty board, 5s timeout keeps local if no compatible leader answers); mid-group any PERMITTED member's edit broadcasts the full snapshot (permissions ride the snapshot; receivers reject STATE from unpermitted senders by their own current belief), last-write-wins with a Lamport rev + sender-name tiebreak so simultaneous edits converge. Unpermitted clients pin their fingerprint each poll (local drift never broadcasts, even after a later promotion) and push own-role changes over a dedicated `ROLE` message everyone accepts (own role only, `lastOwnRoleSent` stops apply-echo); `OBSERVE` is evidence, not a board edit, so it is permission-independent. `PLAYER_ENTERING_WORLD` (+3s; roster unreliable at fire time) re-runs the handshake — members redo the HELLO pull; the leader announces with a STATE broadcast and, once per cold session, requests one group RANKS/VERSION announcement per peer to rebuild the ephemeral directory for everyone — because reload/login wipe `syncPeers` and `GROUP_JOINED` doesn't fire then. Rev is wall-clock-seeded (`max(rev+1, GetServerTime())`): a plain counter reset to 0 on reload and every fresh-session broadcast lost to the old session's higher revs. Change detection = 2s fingerprint poll of the synced slice (write paths are too scattered to hook; view dropdowns mutate entries in place via a local repaint). Applying a remote board updates the fingerprint first so it never echoes back. `/wdw sync` = manual push (leader) / pull (member). `WhoDoesWhat.LOG_SYNC` chat-logs traffic. Protocol versioned (`PROTOCOL`); mismatches warn once and ignore each other.
* **Shared paladin strategy:** `Snapshot()` exposes `db.profile.paladinBuffRules` as `state.paladinStrategy`; it participates in the board fingerprint, leader join replacement, revisions, and permission-gated editing. It is cleared on group leave. `PruneDepartedAssignments()` also removes `prefer` rules whose named paladin left; the existing debounced roster lifecycle elects the leader as the sole housekeeping writer, so views remain read-only renderers and the normal fingerprint poll sends one resulting `STATE`.
* **DB shape (Core.lua):** `assignments` (name→role), `talentSpecs`, `paladinBuffTalents` (+`buffTalentScanVersion`), `warlockHealthstoneTalents`, `coreBuffTalents` (including Gift, Fortitude, and Thorns improvement ranks), `raidAssignments` (row id→name), `paladinBuffRules`, `tankAssignments` (one row per tank: `{player, markers={...}, custom}`; a one-off OnInitialize migration merges the old one-row-per-marker shape by player; Sync's `PROTOCOL` is 9)/`ccAssignments`/`mdAssignments`, `roleCustomizations` (`{buffOrder, allowedCount}`; missing counts are legacy-compatible), `customRoles` (+counter), `permissions` (mode + assistant), `settings`.

* **Addon version discovery:** `Core.lua` reads `WhoDoesWhat.VERSION` from TOC metadata and every Sync message carries it. With a compatible WDW leader, ordinary HELLO receivers stay silent and the leader's initial STATE includes its current peer/version/utility-rank directory. A cold leader reload requests one group RANKS or VERSION announcement per peer to rebuild that ephemeral directory for everyone. Without a compatible leader, stable peers retain the old RANKS/VERSION whisper fallback so presence remains discoverable; clients which are themselves awaiting reload sync stay silent to prevent mutual fanout. The main title shows the standard warning icon when a current group member reports a higher numeric version. In unpackaged source only, Developer → Simulate newer addon version makes that client display, advertise, and compare as the next patch version so a current-version peer sees the out-of-date warning. Every simulator entry point is inside BigWigs `--@do-not-package@` blocks and is removed from release archives.

* **PallyPower talent fallback:** incoming `SELF` reports provide immediate Improved Wisdom/Might ranks and Kings/Sanctuary availability for otherwise-unknown paladins. These tables carry `_source="pallypower"`, are not relayed over WDW sync, and are replaced wholesale (tag removed) by a native scan or authoritative WDW rank message. PallyPower does not report tree totals or spec. Paladins with no native, synced, or external buff-talent data are excluded from WDW's blessing matcher; their rows sort first as `Awaiting talents`, while the leading warning tooltip suggests Rescan or marking someone who is sitting out as Non-raider.

## Releases (CurseForge automatic packaging)
* A GitHub push webhook feeds the CurseForge packager, configured to package **tagged commits only** — pushes to `main` are free, a release happens only when a tag lands.
* To cut a release: commit, then `git tag 1.0.5 && git push origin 1.0.5`.
* Tag text becomes the packaged `## Version:` through `@project-version@`. Use plain `1.0.5`, **no `v` prefix**. A tag containing `beta`/`alpha` (for example `1.1.0-beta`) packages as a Beta/Alpha build instead of a Release.
* Before the release commit, set the TOC debug block's literal `## Version` to exactly the intended tag and add the dated release summary to `Views/AboutView.lua`'s `RELEASES` table. The live main-window title, About window, and peer-version warning read this metadata/history; packaging comments the debug block and substitutes the tag into the earlier `@project-version@` line.
* Keep the version simulator inside `--@do-not-package@` blocks and confirm its setting name is absent from the generated release directory before tagging.
* `.pkgmeta` zips as `WhoDoesWhat/` and strips repo-only files (README.md, AGENTS.md, DEVELOPMENT.md, .vscode, .pkgmeta); `Libs/` ships as committed (no externals).
* `## Interface:` remains literal. CurseForge documents `@project-version@`, but does not document an equivalent token that discovers the current WoW Interface number. Revalidate and update the literal after relevant client patches.
* References: [CurseForge automatic packaging](https://support.curseforge.com/support/solutions/articles/9000197281) and the [BigWigs packager](https://github.com/BigWigsMods/packager).

## Historical client observations (revalidate before relying on them)
* The addon currently targets Interface `20505` for TBC Anniversary. Confirm the current client value after patches; an outdated value can mark the addon out of date.
* Modern Menu API exists: `Menu.ModifyMenu`, `MenuUtil.Create*` + `rootDescription:Insert(desc, index)`. Submenu parents need non-nil click callback.
* `SetPartyAssignment` protected (Blizzard-UI only); `ClearPartyAssignment` is callable. `UnitSetRole` is callable by addons only out of combat as of 2.5.6.
* Raid tab rows are `RaidGroupButton<i>` (i = roster index); `RaidGroup<g>Slot<s>` are empty slots. `Blizzard_RaidUI` is load-on-demand; do not load or open it from addon execution on current builds.
* LibClassicInspector's talent ranks are unreliable on Anniversary (2.5.x): native `GetTalentInfo(tab, i)` index order is unstable, but the lib reads its positional cache assuming static order → ranks land under the wrong talent. Read ranks from native `GetTalentInfo` matched by `(tier, column)` instead (only valid during the lib's inspect or for the local player). NovaRaidCompanion does the same (sorts by row/column).
* `TALENTS_READY` fires only on data arrival, never on roster changes — rejoiners need manual cache replay.
* `UIDropDownMenuTemplate`: ~15px transparent padding/side, label 7px from left / 43px from right — ~69px floor for icon-only box. `StyleDropdown` trims the native 64px housing textures to 57px and moves the housing down 3px for every addon-owned dropdown; it leaves the arrow 0.5px lower and nudges it right 2px, while leaving the text 2.8px lower. Assignment controls also opt into left-aligned labels extended 5px toward the left edge through `SectionKit.LeftAlignDropdown`.
* Scroll children need explicit `SetPoint` or won't render until moved; sibling frames render in unstable order — set explicit `SetFrameLevel` on section boxes.
* Blizzard UI source: github.com/Gethe/wow-ui-source branch `classic_anniversary`.
